# Baseline 협업 안내

<a id="git-handoff"></a>

## GitHub 두 사람 인수인계 — 2026-09-27

[협업 폴더](../collaboration/README.md)는 백가온·박민수의 push별 변경사항과 의견을 전달하는 임시 수신함이다. 아직 양쪽 확인이 끝나지 않은 건만 `collaboration/pending/`에 남긴다. 원고·분석·공통 규칙의 기준 위치를 이 폴더로 옮기지는 않는다.

### 1. 내용 변경을 공유하는 사람이 준비한다

- 실질적인 파일 변경을 공유하는 push마다 `pending/<YYYYMMDD-HHMMSS-작성자-주제>/` 하나를 만든다. 시각은 KST, 작성자는 `gaon` 또는 `minsu`처럼 파일명에 쓰기 쉬운 표기를 쓰되 실제 이름을 본문에 남긴다. 같은 ID가 있으면 새 식별자를 쓰며 덮어쓰지 않는다.
- 폴더에는 `changes.md`, `백가온.md`, `박민수.md`를 둔다. 변경사항에는 무엇을 왜 바꿨는지, 파일 범위, 확인한 것·못 한 것, 보류·다음 요청, 데이터 제외 여부를 적는다. 각자의 의견·읽음은 각자 파일에 기록한다.
- push 전은 `DRAFT`다. 실제 내용 커밋 C를 만들어 공유한 뒤 성공을 확인하고 `OPEN`, 전체 C 해시, 브랜치·확인 시각을 후속 기록으로 남긴다. 원격을 확인하지 않았다면 완료로 단정하지 않는다. 기록 파일에 그 파일을 포함하는 커밋 자신의 해시를 넣으려 하지 않는다.
- 의견·읽음·전송 확인만 바꾸는 push는 같은 인수인계를 갱신한다. 삭제 정리만 하는 push는 삭제 커밋 메시지로 설명한다. 인수인계를 기록하기 위한 인수인계를 계속 만들지 않는다.
- 변경사항 작성자가 각자의 의견을 추정해서 채우지 않는다. 상대의 원고·코멘트도 임의로 수정하지 않는다. 양식·안내는 영구 유지한다.

### 사용자가 따로 전달하라고 지정한 코멘트

- 작업 중 “협업 폴더에 넣어줘”, “이 내용은 내 코멘트로 남겨줘”라고 지정한 내용은 관련 대기 인수인계의 해당 팀원 파일 안 `사용자 전달 코멘트` 절에 저장한다. `changes.md`의 변경 요약·일반 검토 코멘트·보조 도구의 해석과 섞지 않는다. 변경 요약에서는 필요할 때 코멘트 위치만 연결한다.
- 현재 말하는 팀원과 대상 인수인계가 대화에서 명시적으로 확인되어 있으면 그 정보를 사용하고 반복 질문하지 않는다. 확인되지 않은 이름·여러 대상 중 하나를 추정하지 않는다. 모호한 항목만 질문하고, 확인 전에는 어느 팀원의 코멘트로도 배정하지 않는다. 해당 대기 건이 없으면 작성자·대상을 확인한 뒤 기존 양식으로 새 `DRAFT`를 준비한다.
- 항목별로 순번·요청일·전달자·분류·원문 출처를 기록한다. 분류는 `의견`, `질문`, `제안`, `요청`, `확정 결정` 중 내용에 맞게 원문 밖에 붙인다. `확정 결정`은 실제 확정한 경우에만 사용하며, 불명확한 분류는 미분류로 남긴다.
- 지정된 문구는 기본적으로 원문 그대로 인용하고 기존 항목 뒤에 추가한다. 요약·윤문은 사용자가 요청했을 때만 하며 그 사실을 표시한다. 필요한 보조 설명은 별도 절에 두어 사용자의 말과 구별한다. 이전 항목을 조용히 덮어쓰지 않는다.
- ‘사용자 전달’은 그 팀원이 전달을 요청했다는 뜻이다. 보조 도구의 설명이나 제삼자 자료를 옮겼다면 원문 작성 주체·출처를 함께 표시한다. 전달 요청만으로 사용자가 직접 쓴 말·동의한 의견·실행을 승인한 결정이라고 바꾸지 않는다.
- 실제 코멘트를 추가·수정하면 해당 코멘트 버전을 올리고, 상대의 이전 버전 읽음 확인은 유효하지 않은 것으로 취급한다. 빈 절·양식만 추가한 것은 코멘트 작성이나 읽음 확인이 아니다. 코멘트 저장 자체로 본인·상대의 읽음란을 완료 처리하지 않는다.
- 저장 후 사용자에게 `백가온 전달 코멘트` 또는 `박민수 전달 코멘트`로 별도 표시하고 분류·저장한 본문·파일 경로를 보여준다. 작업 변경 요약과는 별개로 보여주며, 실제 저장 전에는 저장했다고 말하지 않는다. 로컬 코멘트 저장은 Git push·외부 전송 허가가 아니다.

### 2. 읽음 판정은 명시적인 버전 확인으로 한다

새 협업 작업에서 미확인 인수인계와 상대 코멘트, 관련 변경 파일을 읽는다. 읽음을 기록하려면 누구의 입장인지 사용자가 지정했거나 본인이 직접 기록해야 한다. 이름 순서·PC 계정·Git 작성자 설정만으로 현재 팀원을 추정하지 않는다.

각 팀원의 확인에는 다음이 모두 필요하다.

- 본인 이름, 실제 확인 시각과 확인 주체, 읽은 핵심 내용·다음 행동.
- 읽은 `changes.md` 내용 버전과 실제 공유 내용 커밋 C.
- 읽은 상대의 코멘트 버전. 빈 코멘트는 의견 없음이 아니며, 본인 의견이 없으면 `추가 의견 없음`을 작성한다.

파일 열기·pull·클론·시간 경과만으로 읽음 처리하지 않는다. 보조 도구는 해당 팀원을 대신해 실제 읽도록 요청받았을 때만 `백가온의 요청에 따른 도구 대리 열람`처럼 기록할 수 있다. 도구 열람을 사람이 읽었다는 증거로 쓰지 않는다. **읽음은 내용에 동의한다는 뜻이나 편집·분석·게시 재개 허가가 아니다.**

`changes.md`의 의미 있는 내용이 바뀌면 내용 버전을 올리고, 의견 본문이 바뀌면 해당 코멘트 버전을 올린다. 읽음 시각·확인란만 수정하는 경우에는 버전을 올리지 않는다. 현재 내용 버전·C 또는 상대 코멘트 버전과 맞지 않는 확인은 다시 읽기 전까지 유효하지 않다. 이렇게 확인란 변경만으로 서로 무한 재확인하는 일을 피한다.

### 3. 확인이 끝난 인수인계만 지운다

다음 조건을 전부 만족한 건만 인수인계 정리 시 삭제한다.

1. 실제 공유가 확인된 `OPEN`이고, 두 사람 모두 자기 코멘트를 작성했으며 최신 내용 버전·C·상대 코멘트 버전을 확인했다.
2. 질문·충돌이 해결됐거나 보류 사유·담당자·다음 행동을 해당 `column.md` 또는 담당 guide·모델 문서에 옮겼다. 중요한 결정·남은 작업의 유일한 사본이 대기 폴더에만 있으면 삭제하지 않는다. 이관 내용까지 양쪽이 확인한 버전에 포함되어야 한다.
3. **마지막 의견과 양쪽 확인까지 포함한 완성본이 커밋 S로 저장되어 실제 원격 공유 브랜치에서 확인된다.** 로컬 미커밋, 로컬 커밋만 존재, push 미확인은 보존 완료가 아니다. S를 자기 자신 안에 기록하지 않고 다음 삭제 커밋 메시지에서 참조한다.
4. 삭제 직전 최신 공유 상태와 로컬 변경을 확인한다. 마지막 확인 이후 새 의견·수정·충돌이 있으면 중단하고 먼저 읽어 반영한다. 강제 push나 삭제/수정 충돌의 일괄 덮어쓰기로 해결하지 않는다.

삭제 범위는 해당 `collaboration/pending/<정확한 ID>/` 안의 인수인계 파일뿐이다. 실제 절대 경로가 `pending/` 하위인지 확인하며, 저장소 루트·원고·데이터·모델·과거 실행·영구 README·양식은 삭제 대상이 아니다. 미추적 파일이나 설명되지 않은 파일이 섞여 있으면 멈춘다. 전체 협업 폴더를 한 번에 비우지 않는다.

삭제 커밋 메시지에 인수인계 ID, 내용 커밋 C, 보존 커밋 S, 두 확인자를 남긴다. 별도 보관 폴더로 복제하지 않는다. Git 이력 삭제·강제 push는 하지 않으며, 기록은 공유 이력이 유지되는 한 S에서 확인할 수 있다. 최신 작업 폴더에서는 사라져도 과거 Git 기록까지 지우는 방식이 아니다.

열람용 명령 예시(실제 ID·S로 치환; 삭제 명령이 아님):

```text
git log --all --full-history -- "collaboration/pending/<인수인계 ID>/"
git show <보존 커밋 S>:collaboration/pending/<인수인계 ID>/changes.md
```

자동 감지·백그라운드 삭제·Git hook은 사용하지 않는다. 작업자가 위 조건으로 판단한다. 삭제 후에는 무엇을 지웠고 어느 커밋으로 복원 가능한지 보고한다. Git 커밋·push는 별도 명시적 요청 범위에서만 수행하며, 필요한 보존 조건을 충족할 권한이 없으면 기록을 남겨둔다.

### 기준 문서와 연결

- 공통 결정: [AGENTS](../AGENTS.md) 또는 담당 guide. 칼럼 결정·다음 작업: 해당 `column.md`. 모델 정의·상태: `models/`와 실행 manifest.

## GitHub 협업 추가 — 2026-09-16

사용자 요청으로 코드·문서·모델 정의·집계 결과를 GitHub 공유 대상으로 분리한다. [공유 범위](github_sharing.md), [팀원 데이터 준비](data_setup.md), [제외 파일 목록](excluded_files.json)을 따른다. 원본/행별 자료/캐시/설치 라이브러리는 로컬에 유지하며 Git 업로드에서 제외한다. GitHub 업로드는 Google Drive/Docs 동기화가 아니다. 아래는 기존 Drive 운영 규칙이다.


## 저장 위치와 역할

공유 대상: https://drive.google.com/drive/folders/1kIsnL50yB1T7tkCkAqDhAcct9k_sZbVs

- 로컬 Baseline: 작업 지침, 원본 데이터, 정제 과정, 분석 코드와 검증 기록의 기준 위치.
- Google Drive: 팀원이 볼 정제 데이터, 요약표, 차트, 출처 설명, 공동 원고, 발행용 자료.
- Google Docs 공동 원고를 만든 이후에는 Docs가 본문의 최신본이다. 생성 전에는 로컬 `column.md`가 원고 기준이다.
- 업로드한 CSV는 분석 결과 스냅샷이다. 수정 의견은 별도로 기록하고 로컬 분석을 재실행해 새 버전을 공유한다.

## 드라이브 폴더 구조

```text
Baseline/
├─ 협업안내.md
├─ 프로젝트구조.md
└─ 001-first-column/
   ├─ 01-공동원고/          # Google Docs: 집필 시작 시 생성
   ├─ 02-정제데이터/        # 검증된 CSV·엑셀·요약표
   ├─ 03-차트/              # 원고에 쓰는 이미지
   ├─ 04-출처와분석설명/    # 출처·단위·분모·방법·한계
   └─ 05-발행본/            # 검토를 마친 게시용 자료
```

칼럼 번호를 로컬과 드라이브에서 동일하게 쓴다. 주제 확정 시 이름과 링크 기록을 함께 관리한다. 필요한 자료가 없을 때 예시 결과나 빈 공동 원고를 임의로 만들지 않는다.

## 업로드 절차

1. 사용자가 지정한 칼럼과 공유할 자료를 확인한다. 업로드 요청 범위 안에서 실행한다.
2. 정제 데이터의 기간·단위·표본 수·결측·분모와 차트의 출처를 검증한다.
3. 공유 가능한 정제본·설명·차트만 올린다. 원본 데이터는 공유 필요성과 이용 조건을 확인한 경우 포함한다.
4. 데이터·차트 스냅샷은 `이름_YYYY-MM-DD_v01`처럼 버전을 표시한다. 같은 이름을 발견하면 내용을 확인하고 중복 업로드를 피한다.
5. 기존 공동 원고는 팀원 수정 내용을 먼저 읽고 요청한 부분을 반영한다. 로컬 사본으로 덮어쓰지 않는다.
6. 업로드 후 파일 이름·부모 폴더·링크를 확인하고 칼럼의 `collaboration.md`에 기록한다.
7. 사용자에게 로컬 변경과 드라이브 반영 결과를 나누어 보고한다.

## 운영 안내

- 플러그인 연결은 폴더 자동 동기화가 아니다. 현재는 요청에 따른 업로드 방식이다.
- 팀원은 본인 Google 계정으로 초대한다. 팀원 초대나 공개 링크 전환은 별도 요청을 받는다.
- 2026-09-05 연결 확인 시 최상위 폴더에는 소유자 권한만 있었다. 팀원 초대 완료 여부는 실제 권한으로 확인한다.
- 구조나 협업 규칙 변경 시 로컬 README와 관련 지침을 갱신한다. 드라이브 안내 파일은 공유 사본이며, 업로드 성공 시에만 동기화 완료로 보고한다.
